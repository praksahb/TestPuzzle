1. Project Overview
A Unity 2D mobile puzzle game where the player snaps kite-shaped polygon tiles onto a growing cluster. The cluster starts with a single pre-placed center kite. The player drags new kite pieces from floating spawn positions and drops them near the cluster boundary. If the edges align the piece snaps in.
1.1 Game Phases
Phase
Description
Kite Phase
Player snaps kites. Forgiving snap mode. Hat detection runs silently on every snap.
Hat Transition
When 8 kites form a Hat topology, they are destroyed and replaced by a single Hat prefab at the correct position and rotation.
Hat Phase
Player snaps Hat pieces. Strict snap mode. Hat detection continues — future Hat formations from kites are still possible if mixed pieces exist.
1.2 Win and Loss Conditions
Loss: An enclosed gap (empty space fully surrounded by snapped pieces) forms anywhere in the cluster.
Win: None — the game is infinite. Camera zooms out as the cluster grows.
1.3 Center Piece
The scene always starts with one pre-placed center kite at position (0,0,0). Its rotation is set in the Inspector before play. The center piece is always named 'Kite_1_PerfectCollider' (no Clone suffix). All snapped pieces are named 'Kite_1_PerfectCollider(Clone)'. This naming difference is used to identify the center piece reliably in code.
2. Kite Geometry
The kite is a quadrilateral with 4 vertices (P1, P2, P3, P4) and 4 edges. All geometry is read from socket child GameObjects on the prefab — never hardcoded.

2.3 Floating Point Drift
Unity's rotation matrix math compounds outward from the center piece. By the 7th–8th snapped piece, edge midpoint drift of up to 0.025 world units is observed. The spatial hash system in Section 4 handles this. Do not use Mathf.Approximately or Vector2 == for any edge comparison.
3. Snap Modes
3.1 Forgiving Mode (Kite Phase)
Auto-rotates the dragged piece to the nearest valid 30° increment
Auto-closes ALL flush edges on snap simultaneously

3.2 Strict Mode (Hat Phase)
No auto-rotate

4. Edge Slot Registry
4.1 Purpose
The registry is the single source of truth for cluster topology. Every edge in the cluster is OPEN (boundary, free to snap to) or CLOSED (shared between two pieces). All snap decisions go through the registry first.
4.2 Spatial Hash Implementation
⚠ Do not revert to a single-bucket Dictionary. The spatial hash is required to handle floating point drift. This implementation is confirmed working from V3.
const float BUCKET_SIZE = 0.05f;
const float MATCH_DISTANCE = 0.03f;
const float MATCH_LENGTH_DIFF = 0.05f;
Dictionary<Vector2Int, List<EdgeSlot>> spatialSlots;
Vector2Int ToCell(Vector2 midpoint)
  return new Vector2Int(
    Mathf.FloorToInt(midpoint.x / BUCKET_SIZE),
    Mathf.FloorToInt(midpoint.y / BUCKET_SIZE)
  );
EdgeSlot FindMatchingSlot(EdgeKey key)
  Vector2Int cell = ToCell(key.midpoint);
  for dx in [-1, 0, 1]:
    for dy in [-1, 0, 1]:
      search bucket at (cell.x+dx, cell.y+dy)
      for each slot in bucket:
        if Distance(slot.midpoint, key.midpoint) < 0.03f
        && Abs(slot.length - key.length) < 0.05f
          return slot
  return null
4.3 EdgeSlot Structure
EdgeSlot
  EdgeKey key          — midpoint + length
  bool    isOpen       — true = boundary, false = shared
  Piece   ownerA       — first piece claiming this edge
  Piece   ownerB       — second piece (set when CLOSED)
4.4 Key Operations
void BootstrapFromCluster(List<Piece> pieces)
  Physics2D.SyncTransforms()  // REQUIRED before reading any socket positions
  For each piece: read socket world positions
  For each edge: compute midpoint and length
  If another piece shares this edge: mark CLOSED
  Else: add as OPEN
void RegisterPieceEdges(Piece piece, Vector2[] canonicalVerts)
  For each edge of piece:
    existing = FindMatchingSlot(edge)
    if existing != null and existing.isOpen:
      existing.isOpen = false
      existing.ownerB = piece
    else:
      add new OPEN slot for this edge
void UnregisterPiece(Piece piece)
  Remove all slots where ownerA == piece or ownerB == piece
  Re-open any CLOSED slots that had this piece as one owner
4.5 Physics2D.SyncTransforms Requirement
⚠ Always call Physics2D.SyncTransforms() before reading socket world positions in BootstrapFromCluster. Without this, Unity may return stale transform values for pieces placed before the physics step.
5. Geometry Snapper
5.1 Snap Pipeline (Forgiving Mode)
Sanitize piece rotation to nearest 30° increment on Z axis only
For each edge of dragged piece: call registry.FindBestMatchingOpenSlot()
If no slot found: fire OnSnapRejected(NoOpenSlotNearby), return false
ComputeCandidatePose() — compute target position and rotation
ProjectAllEdges() — project ALL edges to candidate pose
FindAllMatchingOpenSlots() — identify expected neighbours
ConfirmNoBodyIntrusion() — check against non-neighbours only
If intrusion found: fire OnSnapRejected(BodyOverlap), return false
Apply position and rotation to piece
Read canonical vertices BEFORE SetParent
SetParent to CoreCluster
RegisterPieceEdges() with canonical vertices
Fire OnSnapSuccess
5.2 ComputeCandidatePose — Dual Mapping
Try both edge direction mappings and pick the one with smaller angular error:
Mapping A: dragEdge.p1 → slot.p2, dragEdge.p2 → slot.p1
Mapping B: dragEdge.p2 → slot.p2, dragEdge.p1 → slot.p1
Pick mapping with smaller angleDiff
5.3 Mirror Awareness
When a piece has eulerAngles.x ≈ 180 or eulerAngles.y ≈ 180, it is mirrored. For mirrored pieces, swap p1 and p2 on all edges before registry matching. This preserves the correct edge direction convention regardless of mirror state.
5.4 Body Intrusion Check
Only check against non-neighbours. Expected neighbours are pieces that share a CLOSED edge with the incoming piece after registration. Excluding them prevents false rejection when a piece fills a concave pocket touching multiple existing pieces.
5.5 Canonical Vertices
⚠ Read canonical vertices BEFORE calling SetParent. If CoreCluster has any transform offset, reparenting shifts socket world positions and the registry stores wrong midpoints.
// CORRECT order:
Vector2[] verts = GetCurrentWorldVertices(piece);  // before SetParent
piece.transform.SetParent(coreCluster.transform);
registry.RegisterPieceEdges(piece, verts);
6. Gap Detector
6.1 Purpose
Detects enclosed empty regions in the cluster after every snap. An enclosed gap triggers game over.
6.2 Algorithm
Collect all OPEN edge midpoints from registry
Build adjacency graph of open edges by shared vertices
Find connected components of open edges
For each component: compute enclosed area using shoelace formula
If any component area < gap threshold AND component is fully enclosed: game over
6.3 Gap Area Threshold
Default: 50% of one kite area, computed from canonical vertices at bootstrap time. Gaps smaller than this are ignored to avoid false positives from floating point imprecision at vertices.
6.4 Pinch Point Policy
If the cluster boundary touches itself at exactly one vertex (figure-8 shape), this is NOT game over. Only fully enclosed regions count. GapDetector must handle degree-4 boundary nodes correctly.
7. Hat Pattern Matcher
⚠ This section replaces the entire V3 HatPatternMatcher. The V3 implementation had a bypassed isomorphism check and wrong degree sequence. Do not reuse V3 code here.
7.1 The Hat Monotile — Correct Topology
The Smith Hat monotile is composed of 8 kites from the [3.4.6.4] Laves tiling. The correct internal adjacency graph has these properties:
Exactly 8 pieces (nodes)
Exactly 9 closed internal edges (connections between pieces)
One CENTER piece with degree 4 (touches 4 other pieces on all its edges)
Two BRANCH pieces with degree 3
Three MIDDLE pieces with degree 2
Two TERMINAL pieces with degree 1
Sorted degree sequence: [4, 3, 3, 2, 2, 2, 1, 1]
⚠ The V3 degree sequence [2,3,2,2,2,2,3,2] was WRONG. It described a boundary walk, not the internal adjacency graph. The correct sequence is [4,3,3,2,2,2,1,1].
7.2 The Degree-4 Center Piece
The center piece (degree 4) is the kite that is completely surrounded by 4 other kites — all 4 of its edges are shared (CLOSED). This is the starting center kite when the player builds the Hat naturally around the pre-placed piece. The degree-4 piece is identified by finding the node in the matched subgraph with exactly 4 closed edges to other nodes in the same subgraph.
7.3 Detection Algorithm
Check CLOSED edge count in registry. If < 9, return early. This is O(1) and prevents unnecessary work.
Find connected component starting from the newly snapped piece using BFS over CLOSED edges.
If component size != 8, return no match.
Count CLOSED edges that are internal to this component (both owners in component). If count != 9, return no match.
Compute degree of each node (count internal closed edges per piece).
Sort degrees. If sorted sequence != [4,3,3,2,2,2,1,1], return no match.
Run isomorphism check against known Hat adjacency graph (Section 7.4).
If isomorphism passes: identify degree-4 node, compute centroid, compute spawn rotation, return match.
⚠ Step 4 (internal edge count == 9) is a critical guard against false positives. A symmetric 8-kite flower shape has 10 internal edges and the same degree sequence — it must be rejected here.
7.4 Hat Adjacency Graph
The canonical Hat adjacency (0-indexed, where node 0 is the degree-4 center):
HatAdjacency = [
  (0,1), (0,2), (0,3), (0,4),   // center touches 4 others
  (1,2),                          // branch-branch connection
  (2,5),                          // branch-middle
  (3,6),                          // branch-middle
  (4,5),                          // branch-middle
  (6,7),                          // middle-terminal
]
NOTE: This produces degree sequence: node0=4, node1=2, node2=3, node3=2, node4=2, node5=2, node6=3, node7=1. Wait — recount: (0,1),(0,2),(0,3),(0,4),(1,2),(2,5),(3,6),(4,5),(6,7) = 9 edges. Degrees: 0→4, 1→2, 2→3, 3→2, 4→2, 5→2, 6→2, 7→1. Sorted: [4,3,2,2,2,2,2,1]. Adjust adjacency during implementation to match confirmed degree sequence [4,3,3,2,2,2,1,1].
⚠ The exact adjacency array must be validated against the physical kite layout in Unity before finalising. Build the Hat manually, log all closed edge pairs, and derive the adjacency from real data. Do not trust any adjacency graph that has not been verified against actual gameplay logs.
7.5 Isomorphism Check
The isomorphism check verifies that the detected 8-piece subgraph matches the Hat adjacency graph structurally — not just by degree sequence. Use Ullmann's algorithm or VF2 for subgraph isomorphism. The check must NOT be bypassed. If it fails for a valid Hat formation, the adjacency graph in Section 7.4 needs correction, not the check itself.

7.9 Performance
TryFindHat is called after every successful snap. Performance is critical.
Step 1 early exit (CLOSED < 9) fires on almost every snap — O(1)
BFS in Step 2 visits at most 8 nodes once threshold is passed — O(8)
Total cost per snap: effectively O(1) regardless of board size
Never call FindObjectsByType inside TryFindHat — use corePieces list directly

10. Game Manager
10.1 OnHatDetected(HatMatchResult result)
public void OnHatDetected(HatMatchResult result)
{
  InputManager.Instance.SetEnabled(false);
  foreach (Piece p in result.matchedKites)
  {
    CoreCluster.Instance.Registry.UnregisterPiece(p);
    CoreCluster.Instance.RemoveFromCorePieces(p);
    Destroy(p.gameObject);
  }
  GameObject hatGO = Instantiate(
    hatPrefab,
    new Vector3(result.centroid.x, result.centroid.y, 0f),
    Quaternion.Euler(0f, 0f, result.spawnRotation)
  );
  hatGO.transform.SetParent(CoreCluster.Instance.transform);
  Piece hatPiece = hatGO.GetComponent<Piece>();
  Physics2D.SyncTransforms();
  Vector2[] hatVerts = EdgeSlotRegistry.GetCurrentWorldVertices(hatPiece);
  CoreCluster.Instance.Registry.RegisterPieceEdges(hatPiece, hatVerts);
  CoreCluster.Instance.AddToCorePieces(hatPiece);
  CoreCluster.Instance.SwitchToStrictConfig();
  InputManager.Instance.SetEnabled(true);
}

14. Future Versions — Do Not Implement Now
⚠ The following are noted for V5 only. Do not implement any of this in V4.
14.1 Generic Polygon System (V5)
V5 will generalise the system to support any polygon defined by N vertices. The polygon type will be defined by a PolygonConfig ScriptableObject with vertex positions, edge indices, and pattern adjacency data. This will enable Penrose kite+dart, Spectre, and custom tiles without code changes.
14.2 Hat Mirroring (V5 Hat Scene)
The Smith Hat requires mirror images (flipped Hats) for infinite aperiodic tiling. Approximately 1 in 7 Hats must be mirrored. Two implementation options: probabilistic spawner (15% chance of mirrored Hat) or double-tap flip mechanic. Do not implement in V4.
14.3 Penrose Tiles (V5+)
Penrose P2 tiling uses two polygon types: kite (fat quadrilateral, angles 72-144-72-72) and dart (concave quadrilateral with one reflex angle, angles 36-216-36-72). Both tile edge-to-edge with no overlap. The generic polygon system in V5 will handle both naturally.
